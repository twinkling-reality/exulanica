# ADR-0010: OPM evolves to version 2, and placement stays outside the file

- Status: **ACCEPTED and BUILT 2026-09-03.** The coordinated pass is done across both writers,
  both validators, the renderer binding and its two shader sources, the retired `atlas-three`
  reader, the app's production loader and the committed cross-language pin, which was regenerated
  rather than converted. The stage parameter now reads `"container": "opm/2"`, so every point map
  a corpus already held is refused by name and rewritten under a new idempotency key. Two of the
  three measurements this record asks for below have been taken and one of them corrects D4; the
  third, whether the flag removes the fringing, still needs a renderer that consumes it.
- Date: 2026-09-03
- Deciders: Exulanica build. Three independent proposals (evolve in place, keep OPM/1 and add
  side records, replace with an existing format) were scored by judges on the renderer and
  delivery path, on cross-language contract integrity, and on the long term.
- Supersedes: two code-level decisions named in the last section. It does not touch ADR-0003's
  choice of streamed SOG for rung 1.
- Related: [adr/0003-renderer-selection.md](0003-renderer-selection.md);
  [adr/0008-generated-geometry.md](0008-generated-geometry.md);
  [adr/0009-the-ladder-above-rung-3.md](0009-the-ladder-above-rung-3.md);

## Context

### How much of the question is actually open

Less than it appears. Rung 1 delivery is already decided as streamed SOG produced by
`splat-transform`, with PLY never shipped and `.spz` as interchange (ADR-0003). Rung 2 is already
its own SHA-bound corridor artifact with its own wire profile. ADR-0009 places posed multi-view
sets in a separate placement record over unchanged member files. So the only container question
genuinely open is the rung 3 one, and the answer is that it gets exactly one more version.

### Why the container needs a version at all

Six defects converge on the same header, and none of them is fixed by a side record:

1. **The alpha meaning is inferred rather than declared.** Both writers declare `colorAlpha` as
   `confidence`, and one of them now writes a spacing-derived support ratio that its own docstring
   says is not a probability. The renderer tells them apart by the presence of a statistics key,
   which is a format flag that nobody declared as one.
2. **The segment attribute is 2 bytes.** WebGPU requires an element size that is a multiple of 4,
   so the engine pads it per point, and the repository's own renderer notes record the intended
   fix as storing it as 4 bytes in the container.
3. **Exactly three sections are hardcoded** in both validators and the decoder, and the stride is
   the literal 18 in the binding, so the header's own generic section list is a fiction.
4. **The declared aspect was the model's working grid**, which refused every source that was not
   4:3. That is fixed now in the stage, but the header still does not say which grid the points
   came from, so the two facts cannot be checked against each other.
5. **The silhouette drop is invisible per point.** The map records how many points it dropped and
   not which survivors lost a neighbour, and the renderer's tangent-frame estimation needs exactly
   that to avoid fringing at silhouettes.
6. **Two writers disagree**, and the production validator refuses the files the TypeScript writer
   produces. The exact cause was not established here and the fixtures on disk are in fact
   contiguous, so D2 is justified by the five defects above rather than by this one, and closing
   it is a task the implementation must diagnose rather than assume.

Nothing in production stores or serves a `.opm` file: there is no API route for artifact bytes and
the only loader is the development preview. The depth stage is already being re-keyed by an
uncommitted parameter change, so the container version rides a regeneration that is happening
anyway. That window closes with the first real corpus.

## Decision

**D1. Evolve.** `.opm` gets version 2. The magic stays `OPM1`, the JSON header stays, the planar
sections stay and the camera frame stays. It does not fork by rung, because rungs 1 and 2 already
have their own containers, and it is not replaced by glTF or SPZ, because the reading cost is the
same either way while the writing cost and the migration are not, and no external splat format
carries the per-point segment vocabulary this product needs.

**D2. The section list becomes authoritative.** Readers compute every offset and stride from the
header rather than from a constant, and a registered optional section is not a version bump. This
is what makes the header's generic shape true and is the only part of the change that prevents the
next attribute from being another version.

**D3. The segment section becomes a 4-byte `tags` section, two uint16 channels.** Channel 0 is the
segment id, unchanged in meaning. Channel 1 is a flags word. This closes the WebGPU padding defect
by making the element size a multiple of 4, and it is not a new binding shape: it is what the
engine already pads to.

The declared range of a segment id is bounded by what the renderer can actually draw, not by the
width of the field: the semantic table holds sixteen entries, the binding raises for a larger id
and the shaders index a fixed array. So the container declares the same bound the renderer
enforces, and widening it later is a change to both together rather than a header edit that the
renderer silently ignores.

**D4. Bit 0 of the flags word says this point lost a neighbour to the silhouette drop**, written
by the depth stage which is the only place that knows. The remaining bits are reserved and
validated zero. **No normals and no radii are added.** The measurement is the reason: estimating
anisotropic tangent frames at load, by reprojecting each point through the header's own camera,
closed the grazing pavement completely at no per-frame cost, while normals alone measured worse
than the shipped disc. The one thing the renderer cannot recover for itself is the frame at points
whose neighbour was dropped, which is exactly what bit 0 marks. A format change that carried
normals would have paid twelve bytes a point for something worse than free.

**How much this buys is small and is stated rather than inflated.** On the measured map, 201 of
190,570 points had a frame on one axis only and 36 had none, so bit 0 addresses about a tenth of a
percent of points. It is worth four bits of a word that is being added anyway for alignment, and
it would not be worth a section of its own. The visible artefacts it targets, fringing at the
person's silhouette and streaking at the map's edge, are concentrated rather than spread, which is
why they read as defects at all; whether the flag removes them is the thing to measure before
writing it.

**CORRECTED 2026-09-03, on the measurement the paragraph above asked for. The tenth of a percent
is the wrong population, and the flag marks twenty times more.** Regenerating the same photograph
under this container marks 3,943 of 190,570 points, **2.07 percent of the file**
([reconstruction-findings.md](../reconstruction-findings.md) section 5.1). The two numbers count
different things and both are right: 201 is how many points ended up with a degenerate tangent
frame, and bit 0 as this decision defines it marks a point that lost ANY of its four neighbours,
which a point can survive with a usable frame from the neighbour on the other side. Nothing is
lost by the coarser flag, because a point marked on both row neighbours is exactly the degenerate
case and is recoverable at load; what was wrong was the sentence weighing four bits against a
tenth of a percent. The measurement it does not settle is the one that still matters: nothing
consumes bit 0, so whether it removes the fringing is unmeasured and stays that way until a
renderer reads it.

**D5. `colorAlpha` becomes a declared enum**, `support` or `confidence`, and the renderer keys on
it instead of inferring meaning from a statistics key.

**D6. `modelImage` is added, and `viewpoint.aspect` keeps meaning the source camera.** The header
then states both the photograph's dimensions and the grid the points were unprojected from, which
is the fact the renderer needs to rebuild the image grid for load-time tangent frames, and it is
stated rather than inferred from a point count.

**This does not reverse the fix that already shipped.** The 3:2 ingest failure was closed on
2026-09-03 by writing the source aspect in the depth stage, and `viewpoint.aspect` stays the
source camera's aspect for the reason recorded there: the field describes the camera that took the
photograph, and a rounded working grid is an implementation detail of inference. Redefining it as
the model grid's aspect would undo that. `modelImage` is an additional fact, not a replacement,
and the validators check the two for consistency rather than for equality. Any tolerance must be
derived from how the model rounds both dimensions independently rather than assumed to be one
row.

**D7. Placement is not in the file.** The viewpoint stays pinned at the origin looking down the
negative Z axis on both sides. A posed set is a separate digest-bound placement record naming its
members by content hash, per ADR-0009. This keeps a `.opm` file a statement about one camera and
one photograph, which is what makes it verifiable on its own.

**D8. No origin vocabulary.** OPM/2 carries no observed-versus-generated channel, because ADR-0008
refuses generated geometry and a container that anticipated it would be an invitation.

**D9. The migration is refuse and regenerate.** Both validators refuse version 1 by name with a
message naming the regeneration path. There is no upgrade-on-read, because nothing in production
holds a file to upgrade. There is exactly one committed fixture, the cross-language pin at
`web/packages/atlas-react/test/fixtures/python-writer.opm`; the courtyard map is gitignored and is
not a migration target. That pin is regenerated by the writer itself in the same change, on both
sides, because its input is the flat-plane test double rather than a model, so it reproduces
exactly and needs no conversion tool.

## Alternatives rejected

- **Keep OPM/1 and put everything in side records.** The alpha meaning, the padding defect and the
  one-sided flag are per-point facts inside the file; a side record cannot carry them without
  becoming a parallel file that must be kept in step with the bytes it describes.
- **Replace OPM with glTF binary, or with SPZ.** glTF is structurally the closest external match
  and would bring validators and tooling, and the reading cost is about the same because a private
  decoder is still needed for the per-point attributes the engine's own loader drops. Rejected
  because the writing cost and the migration are real, the splat extension it would ride on is
  still a release candidate, and rung 1 already has its format. This is the alternative to revisit
  if the point map ever has to leave this product.
- **Add normals or radii to the container.** Refused on measurement, see D4.
- **A per-point origin or provenance channel.** Refused by ADR-0008.

## Existing decisions this record touches

- **ADR-0003 is untouched on the container question.** Rung 1 stays streamed SOG.
- **Two code-level decisions are superseded by name**: the TypeScript writer's per-section 16-byte
  alignment, which the production validator refuses, and the hardcoded three-section stride in the
  renderer binding. Both are consequences of D2.
- **The corridor artifact is untouched.** Its `reconstruction_digest` still has no writer, and
  ADR-0009 says what it will bind to.
