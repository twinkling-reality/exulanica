== what went wrong, and what it cost
  1. The output directory is a bind mount the host owns, so the container must run as the invoking user.
     First attempt: "PermissionError: [Errno 13] Permission denied: '/out/outputs'". Fixed in
     container/run.sh (--user "$(id -u):$(id -g)").
  2. Triton compiles some of torch's own kernels at run time, so the image needs a C compiler and libc
     headers. First generation: "RuntimeError: Failed to find C compiler" inside torch's
     bmm_outer_product kernel. Fixed in container/Dockerfile (gcc, libc6-dev).
  3. My own tiling wrapper assumed the patched forward returns an object with .sample; this transformer
     answers with a bare tensor. "AttributeError: 'Tensor' object has no attribute 'sample'". Fixed by
     returning the same shape it was given (tuple, .sample, or bare tensor).
     None of the three was findable on the Mac: the dry run exercises the same runner and passes.
  4. About 14 idle minutes, roughly $0.61, spent waiting on a completion watcher instead of reading the
     log when the generation count stopped moving. My own failure, and the second time in one day.
  5. I deleted the instance before pulling the build log and the weights-fetch log, so those two logs no
     longer exist. Every line I quoted from them was quoted while they existed; they cannot be checked
     now. Next time, pull each step's log as that step ends.
  6. The deletion check ran 13 s after the delete request, while the provider still listed the instance
     as DELETING, so scripts/delete-instance.sh printed "IS STILL LISTED" and exited 1. I recorded the
     deletion at 00:05:56Z without re-listing. I read the account again at 2026-09-18T00:20:01Z: "No
     instances in org glendonchin-hq". The proof is that later reading, not the first one, and the
     script should wait for the provider's own removal rather than a fixed 10 s.
  7. While writing the findings file I typed a digest from memory for painted-render a2 instead of
     copying it. I caught it by rewriting every digest from the picks file and verifying each against
     the bytes on disk: one was wrong, seven were right, and all eight now verify. Nothing was
     published from the wrong value.
  8. The module retention numbers I reported to the orchestrator earlier in the session (brick a1 u
     median 100 per cent, and so on) came from an ad-hoc script with a different normalisation and are
     superseded by the committed measure above. This log's numbers are the ones to use.
